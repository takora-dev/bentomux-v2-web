# Information Architecture: Bentomux Landing Page

**Document Version:** v1.3 | **Status:** Implemented — verified by `scripts/smoke.mjs` | **Last Updated:** 2026-09-15 | **Author:** F. Jibran

> **This is SoT #2.** Derived from `docs/srs.md` (SoT #1). Defines pages, sections, anchors, content hierarchy, and navigation. User Flows (SoT #4) reference the page and section IDs defined here.

---

## 1. Purpose

This document specifies how information is organised across the Bentomux landing page: which pages exist, what sections each page contains, in what order, what each section is responsible for communicating, how a visitor moves between sections and pages, and which URLs are canonical.

It resolves three questions that would otherwise be answered inconsistently during implementation:

1. **How many pages?** Three routes, one of which is a single-scrolling page carrying six sections.
2. **In what order does the story unfold?** A fixed section order that takes a visitor from "what is this" to "get notified", with proof placed before the ask.
3. **What owns each piece of information?** Each fact (agent count, license, platform status) is stated in exactly one authoritative section and referenced, not duplicated, elsewhere.

**Traceability:** `SRS: FR-001.1–FR-001.9` (shell, navigation, footer), `SRS: BG-001–BG-006` (business goals), `SRS: NFR-008.x` (SEO).

**Structure rationale:** a single marketing page is correct here. The product is one desktop application with one pre-release status and one conversion goal. Splitting features, agents, and FAQ onto separate routes would force navigation to explain a product a visitor has not yet decided they care about, and would dilute the single scroll that does the selling.

**Density rationale (v1.2):** the page carries six bands rather than ten. Five of the v1.0 bands each restated a claim the hero or the capability rows already made, and the cost was a page nobody reached the end of. The bands that survived are the ones that carry a distinct job: state the promise, state the figures, show the window, prove five claims, take the address, install. Composition follows `DESIGN.md` (repo root), which is a structural reference only — no third-party copy, colour, or asset is reproduced.

**Why the window comes before the claims:** the visitor should see the thing before being told what it does. SEC-012 is the page's only image of the product and it is markup, so it stays legible at any size and cannot go stale like a screenshot.

**Why the capability rows replaced the feature blocks:** a numbered claim with the file it comes from can be checked (`BR-002.1`). Six alternating media blocks could not be. Row 04 carries the agent counts, so the roster survives as a figure rather than as a showcase section.

**Why install now follows the waitlist:** the hero already quotes the install command, so a visitor who wants to install has what they need at the top of the page. The install band exists for the cases that need a choice — Linux, Windows, the manual downloads, and the pin example — and reading it after the form means the ask never blocks the instructions.

## 4. Navigation Structure

### 4.1 Primary navigation (SEC-001)

| Order | Label | Target | Type | Present below `md` |
|-------|-------|--------|------|--------------------|
| 1 | logo + wordmark | `#hero` | Anchor | Yes |
| 2 | Capabilities | `#capabilities` | Anchor | In menu only |
| 3 | Install | `#install` | Anchor | In menu only |
| 4 | GitHub | Repository URL | External | In menu only |
| 5 | Join waitlist | `#waitlist` | Anchor, primary | Yes |

**Rules:**

- NAV-001: Navigation labels must match the target section heading in meaning. `Capabilities` maps to the capability band (`SEC-013`), whose heading is visually hidden because the five rows are the band.
- NAV-002: Anchor order in the navigation must match the vertical order of the sections on the page. Reordering sections requires reordering the navigation.
- NAV-003: The navigation is sticky from `md` upward. Below `md` it collapses to a logo, the primary action, and a menu control.
- NAV-004: The navigation must remain legible over both the hero and the darkest section. This is achieved with a translucent surface and backdrop blur (`BR-001.4`), not by changing the bar's appearance per section.
- NAV-005: External links in navigation open in a new context and announce it (`FR-007.6`).
- NAV-006 (v1.2): The bar carries at most two anchors. The stat strip and the window figure have no anchor and are not in the bar: they are bands the visitor scrolls through, and a link to them would be a table of contents entry rather than a destination.

### 4.2 Footer navigation (SEC-010)

| Group | Links |
|-------|-------|
| Product | Capabilities, Install (built from `src/content/nav.ts`, so it cannot drift from the bar) |
| Project | Repository, Issues, Discussions, License |
| Legal | Privacy policy, Trademark notice (text, not a link) |
| Contact | `mailto:` address |

### 4.3 Navigation between pages

| From | To | Mechanism |
|------|----|-----------|
| Any section | `/privacy` | Footer legal group; the only route out of `/` besides external links |
| `/privacy` | `/` | Logo in the page header and a "Back to home" link |
| PAGE-003 | `/` | Primary action button |
| PAGE-003 | Repository | Secondary action button |

### 4.4 No return-to-top control

Deliberate omission. The footer already contains every anchor in the product group, and the navigation bar is sticky, so a floating return-to-top control would duplicate an existing affordance and compete with the sticky primary action for attention.

### 4.5 Anchor inventory

The page defines exactly five anchors, in page order: `hero`, `capabilities`, `waitlist`, `install`, `footer` (`src/content/sections.ts`). The skip link targets `#main`, the `main` element, and is not one of them. Any other anchor is a bug: a link to a band that no longer exists is a broken promise, and the smoke run fails on the retired ids.

## 5. Content Hierarchy

### 5.1 Heading outline (PAGE-001)

Exactly one `h1`. Sections use `h2`. Items inside sections use `h3`. No level may be skipped.

```
h1  Run every coding agent in one window                          (SEC-002)
h2  Bentomux at a glance           (visually hidden)              (SEC-011)
h2  the window, with nobody sitting at it                         (SEC-012)
h2  What the window does that a terminal tab does not   (visually hidden)  (SEC-013)
  h3  {capability row title}  ×5                                  (SEC-013 rows)
h2  Be there on release day                                       (SEC-007)
h2  Install Bentomux on your machine                              (SEC-006)
h2  Footer                                       (visually hidden) (SEC-010)
```

**Rules:**

- HIER-001: The `h1` exists once and only once per page.
- HIER-002: An anchored section's heading is the target of its anchor link. Where a band's heading is visually hidden (`SEC-011`, `SEC-013`, and the footer) the `h2` still exists as the region's accessible name.
- HIER-003: Capability row titles in SEC-013 are `h3` because they are peers within one `h2` section, not independent sections.
- HIER-004 (v1.2): A band whose rows are self-evident takes a visually hidden `h2` rather than a visible heading that repeats row 01. The mock figure's label is visible because it names a figure rather than summarising the band.
- HIER-005: The footer's `h2` is visually hidden. It exists so the footer is a reachable landmark heading without adding visual noise.

### 5.2 Fact ownership

Each fact is stated once in an authoritative location. Other sections reference it rather than restate it. This prevents the site from contradicting itself when one fact changes.

| Fact | Authoritative section | May be referenced by | Must not be restated in |
|------|----------------------|----------------------|-------------------------|
| Agent detection count (21) | SEC-013 row 04 (`#cap-runtimes`), rendered from `src/content/agents.ts` | SEC-011 stat strip, SEC-002 subheadline | SEC-006, SEC-010 |
| Configurable agent list (9) | SEC-013 row 04 evidence panel | — | SEC-006, SEC-010 |
| Platform support and the install steps | SEC-006 | SEC-002 ribbon, SEC-011 stat strip | SEC-013 |
| License and trademark | SEC-010 | SEC-002 meta line, SEC-011 stat strip | SEC-013 |
| Waitlist purpose and data handling | SEC-007 | PAGE-002 | SEC-002 |
| Star count | SEC-011 stat strip, read from the GitHub API at render time and omitted when the read fails | — | Everywhere else (`BR-002.3`) |
| Repository and contact URLs | `src/content/site.ts` (`SiteConfig`) | Every section | Nowhere — always imported, never typed twice |
| Workspace, tab and agent-state vocabulary | SEC-012 (`src/content/mock.ts`) | SEC-013 rows 01–03 | SEC-002 |

**Row-level rule (v1.2):** a capability row may state its own claim in full, but the evidence panel belongs to that row alone. A second row repeating the same figure is a bug in named ownership, not a stylistic choice.

**Rule FOWN-001:** a section may reference a fact owned elsewhere only by linking to it. It may never restate the number, name, or status.

### 5.3 Copy length budgets

Budgets keep the page in one narrative register and prevent any section from becoming the centre of the page. They are enforced by content review, not by code.

| Element | Budget |
|---------|--------|
| Hero headline | 3–7 words, one sentence, no punctuation beyond a comma; at most one phrase emphasised in the accent colour |
| Hero subheadline | ≤ 30 words |
| Hero ribbon | ≤ 12 words, names the release status |
| Hero meta line | platforms, licence and two links — no sentence |
| Stat strip label | ≤ 6 words per figure |
| Figure caption | ≤ 25 words |
| Capability row title | 3–10 words, one sentence |
| Capability row claim | ≤ 45 words |
| Capability evidence panel | names the surface, not the claim — rows and chips, no prose beyond one note line |
| Section heading | 3–10 words |
| Section introduction | ≤ 40 words |
| Footer legal block | ≤ 40 words |

## 6. URL Structure

| Pattern | Route | Notes |
|---------|-------|-------|
| `/` | PAGE-001 | No trailing-slash variant served; the alternate form redirects |
| `/privacy` | PAGE-002 | Lowercase, single word, no file extension |
| `/sitemap.xml` | Generated | Lists `/` and `/privacy` only |
| `/robots.txt` | Generated | Permits all except `/api/` |
| `/api/waitlist` | Endpoint | `POST` only. Excluded from sitemap and disallowed in `robots.txt` |
| `/*` | PAGE-003 | Catch-all not-found. Served with a non-200 status and `noindex` |

**Rules:**

- URL-001: All absolute URLs derive from `NEXT_PUBLIC_SITE_URL` (`SRS BR-001.3`). No absolute URL may be written literally anywhere in the codebase.
- URL-002: Anchor IDs are lowercase, single-word, and stable: `hero`, `capabilities`, `waitlist`, `install`, `footer`. The retired v1.1 anchors (`agents`, `features`, `palettes`, `faq`, `community`) are gone and must not be reintroduced as links; the smoke run fails if any of them reappears in the served HTML.
- URL-003: Renaming an anchor is a breaking change. External links to anchors may exist, so a rename requires keeping the old ID as a redirect alias or accepting the break explicitly.
- URL-004: Routes contain no dates, versions, or campaign parameters. UTM handling is the responsibility of the linking platform, not the site.
- URL-005: The site serves no trailing-slash alternates and no uppercase variants. A single canonical form is enforced at the framework configuration level.
- URL-006: `/privacy` is the only route whose content changes independently of a deploy. Its "last updated" date is content, not the build date.

## 7. Section Specifications

### SEC-001 Navigation bar

- **Purpose:** orientation and persistent access to the primary action
- **Content:** logo, wordmark, two anchors, GitHub link, primary action
- **Layout:** single row, logo left, anchors and external link right, primary action far right
- **States:** default (translucent) and scrolled (more opaque, subtle border appears)
- **Responsive:** `md` and above shows anchors inline; below `md` collapses to menu control
- **No-JS:** anchors are plain links and work; the menu is a native `details`, so it works with scripting off; the primary action remains visible
- **SRS:** FR-001.3, FR-001.4, FR-001.5

### SEC-002 Hero

- **Purpose:** state the product's promise, quote the install command, and offer the one action that leaves the band
- **Content, in order:** status ribbon linking to `#install`; eyebrow; `h1` with one phrase in the accent colour; subheadline; the install command quoted from `ENT-005` with a copy control and a note saying which platforms it covers; a meta line carrying the platform list, the licence, a link to `#install`, and a "New · Join the waitlist →" hook
- **Layout:** single column, left-aligned, capped at a readable measure; the command block spans the measure
- **Must not:** exceed one viewport height in a way that hides the command block or the waitlist hook on a 1440×900 desktop
- **Removed in v1.2:** the framed screenshot (`public/screenshot.png`), the secondary "Star on GitHub" button and the hero's telemetry caption. The window is shown in `SEC-012` instead, and the star action moved to `SEC-011` and the navigation bar.
- **SRS:** FR-001.1, FR-001.2, FR-001.7, FR-001.9, FR-002.7, BR-001.1

### SEC-011 Stat strip

- **Purpose:** four figures, stated early and stated honestly
- **Content:** GitHub stars (read at render from `api.github.com/repos/takora-dev/bentomux-v2`, revalidate 3600, **omitted entirely when the read fails**), agent CLIs detected (21, from `src/content/agents.ts`), platforms (3, from `ENT-010`), licence (`MIT`, from `SiteConfig`)
- **Layout:** four cells in one hairline-bordered row; two columns below `md`
- **Heading:** visually hidden `h2` — the figures are the band
- **Each figure:** a number, a label, and a destination (repository, `#capabilities`, `#install`, licence file)
- **Must not:** show a figure the project cannot stand behind. No download count, no install count, no contributor count (`BR-002.3`)
- **SRS:** FR-002.7, BR-002.3

### SEC-012 Application window figure (FIG-001)

- **Purpose:** show the product rather than describe it, and do it without a raster asset
- **Content:** a markup mock of the application window — three workspaces with their branches and states, tabs per workspace, and a pane showing that tab's output. The sidebar lists workspaces only: the application has no agent panel, because a runtime belongs to the tab that runs it. The three-row agent list this section carried until v1.2 is **Removed** (2026-09-14): it named a surface the product does not have.
- **Interaction:** sidebar and tab entries are buttons that swap the pane. The mock is a `group` of `aria-pressed` buttons, **not** an ARIA tablist: nothing behind it is running, and a tablist would promise otherwise
- **Motion (MOT-004):** a braille spinner ticks every 80ms and the working timer every 1s, both starting only after hydration and both stopped under `prefers-reduced-motion: reduce`. No other motion, no persisted state
- **Labels:** a visible band label above the frame, one hint ("click a workspace"), and one caption below
- **No-JS:** the first workspace, its first tab and the full pane text render in the served HTML, so the figure is readable without scripting
- **SRS:** FR-002.2, FR-002.3, FR-002.5, NFR §5.1

### SEC-013 Capability rows

- **Purpose:** state five claims and carry the evidence for each one
- **Content, per row:** number, title, claim paragraph, and an evidence panel
- **Rows (fixed order):**
  1. `#cap-persistent` — persistent workspaces, tabs and PTYs with scrollback
  2. `#cap-state` — live idle / working / blocked state per tab
  3. `#cap-approvals` — the approval overlay and the hook bridge
  4. `#cap-runtimes` — runs the CLIs already on `PATH`; carries the derived detected and configurable counts
  5. `#cap-remote` — the optional monitor, paired by QR code
- **Evidence panel kinds:** `tabs`, `states`, `approval`, `runtimes`, `machines` (`src/content/caps.ts`). One kind per row; a new claim needs a new kind, not a paragraph added to an existing one
- **Layout:** two columns from `lg` (claim left, evidence right), stacked below; a hairline between rows
- **Heading:** visually hidden `h2` — the rows are the band (`HIER-004`)
- **Honesty constraint:** a claim must describe behaviour the application ships as of the site's last content review. The repository-evidence line was cut on 2026-09-15, so the check is a content review against the application repository rather than a rendered path (`BR-002.1` as amended).
- **Removed in v1.2:** the six feature blocks (`SEC-004`) and the agent showcase (`SEC-003`). Row 04 absorbed the roster; the other five claims absorbed the feature blocks.
- **SRS:** FR-002.1–FR-002.6, BR-002.1–BR-002.3
### SEC-006 Install and platform availability

- **Purpose:** take the visitor from the page to a working install on their own machine, using the maintainers' own installer scripts rather than a re-implementation
- **Content:** heading, introduction, OS switcher with three options (macOS, Linux, Windows), one command block per panel with a copy control, per-panel notes, a "what the installer does" list, one manual-download line, a version-pinned example, an x86_64-only note
- **Layout:** switcher above a single panel region; the panel is the dominant element; a command block scrolls horizontally within its own container instead of widening the page
- **Default:** macOS is selected in the server-rendered HTML (`SRS FR-005.2`). A client script may preselect the visitor's platform, but must not override an explicit choice, change text, or shift layout (`SRS FR-005.4`)
- **No-JS:** all three panels are present in the HTML and visibility is decided by CSS from the selected input, so every command is readable and selectable without script (`SRS FR-005.6`)
- **Commands:** the site's short links — `<site>/install.sh`, `<site>/install.ps1`, `<site>/install.cmd` — quoted from the install block of `../Bentomux-v2/README.md`, each answered by a 307 to the matching `installers/*` script. The pin example is the only composed command (`SRS BR-005.1`, `BR-005.2`)
- **Excluded:** the Homebrew line, while the cask does not resolve (`SRS BR-005.6`)
- **SRS:** FR-005.1–FR-005.13, BR-005.1–BR-005.9

### SEC-007 Waitlist capture

- **Purpose:** the primary conversion action
- **Content:** heading, one-sentence promise, email input, submit control, consent statement, result region
- **Layout:** narrow column inside a bordered band on the raised canvas; input and submit inline above `sm` and stacked below
- **Position (v1.2):** the band now follows the capability rows and precedes `SEC-006`. The hero quotes the install command, so the instructions a visitor needs are already at the top of the page and the form no longer stands between them and the install detail.
- **States:** idle, validating, submitting, success, error (`SRS FR-004.3`, `FR-004.8`)
- **Honeypot:** one visually hidden, non-focusable field (`SRS FR-004.7`)
- **No-JS:** form posts to `/api/waitlist` and the endpoint returns a rendered result state (`SRS FR-004.9`)
- **SRS:** FR-004.1–FR-004.9, BR-004.1–BR-004.7

### SEC-009 Community and repository links — **Removed** (v1.2, 2026-09-14)

Was: a heading, an introduction and four equal action cards (Star, Report a bug, Ask a question, Email).

**Reason:** the footer already carried all four destinations, and the navigation bar carries the repository link, so the band was a second copy of the footer. `FR-007.1`–`FR-007.6` are still satisfied; only the surface changed.
